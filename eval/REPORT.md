**但三次都成功了，三份摘要都真实基于 agent_notes.md，没有编造。** 结果对，路径不同。

## 四、上下文增长：为什么每轮越来越贵

全部 8 次运行，**每轮 prompt_tokens 严格单调递增，无一例外**。

| 任务 | 每轮 prompt_tokens | 增量来源 |
|---|---|---|
| task_1 | 859 → 953 → 1390 → 2294 → 2764 | +94（工具结果）→ +437（读 agent_notes.md）→ +904（读旧摘要）→ +470 |
| task_6 | 831 → 914 → 1825 → 2729 | +83 → **+911**（读 python_notes.md）→ +904（读两份旧摘要） |
| task_4 | 833 → 926 → 1009 → 1090 | +93 → +83 → +81 |
| task_5 | 843 → 923 | +80 |

**三个规律：**

1. **第 1 轮是固定底数**：8 次运行的第一轮是 831～859（波动仅 1.7%）。这部分是 SYSTEM_PROMPT + 工具 JSON Schema + 任务文本，跟任务难度无关。
2. **第 2 轮跳得小**：80～104 token，只是加上「模型那句工具调用」+「一个小的工具结果」。
3. **跳得大的一轮，都是读了完整文件的轮次**：读 `agent_notes.md` 加约 437，读 `python_notes.md` 加约 911，读两份旧摘要加约 904。**token 的增量几乎等于被读文件的内容体积。**

**为什么下一轮就更贵**：Agent 的工作方式是「把工具结果回喂给模型」。历史一旦写进去，**之后每一次请求都要把整条历史原样重发一遍**。所以读一个大文件，不只是那一次贵——它会让后面每一轮都永久变贵。

**代价有多大**：全部 46,011 token 里有 **40,816（88.71%）是 prompt**，completion 只占 11.29%。换句话说，**这个 Agent 花的钱几乎全是「重复发送已经说过过的话」**。

task_1_c 比 task_1_b 多花的 7,078 token 里，有 6,453 是 prompt。多读两个文件、多走两轮，成本就这样被堆上去的。

> 本轮只记录，不解决。这是未来 Context Management 阶段的证据。

## 七、当前最大的三个问题

### 1. 成本随轮次机械增长，且 88.7% 的钱花在重复发送历史
每一个任务、每一轮都在变贵，无一例外。读一个大文件会让**之后所有轮次**永久变贵。这是结构性的，不靠调 Prompt 能解决。

### 2. 结果稳定但过程不稳定
同一任务 2.20 倍 token 方差、模型调用数 4～6 浮动、task_1_c 甚至自己重写了一次刚写的文件。用户无法预测一个任务要花多少钱、走几步。目前没有机制给这个「兜底」。

### 3. 87.5% 的任务无法自动判定，且规则漏掉了「不完整」
只有 1/8 任务能完全机器验证。「100% 成功」是个很弱的声明——它只证明了「文件存在、关键词出现了」。Task 3 那种「技术上对、实质上没做完」的回答，规则根本看不见。

**两个次要观察（不影响上述三条）：**
- 重复调用拦截功能 0 次触发。Phase 5.5 修的那个「相同 Tool Call 反复执行」在这 8 次运行里**根本没出现过**——它是那次运行的偶发问题，不是系统性问题。（功能本身正确，有 19 个单测覆盖）
- 步数上限的余量只有 2：最多用到第 6 轮，上限是 8。task_1_c 那次已经证明稍微复杂一点就会逼近上限。
